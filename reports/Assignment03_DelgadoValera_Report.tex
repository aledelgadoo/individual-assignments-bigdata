\begin{abstract}
\noindent\textbf{Question:} how does the number of threads $p$ affect a dense
matrix multiplication on shared memory, when does it beat sequential
execution, and what does SIMD vectorisation add on top of threads? We compare
an equivalent sequential baseline with an OpenMP row-parallel implementation
of the same validated \texttt{ikj} kernel (same \texttt{float64} data,
inputs and arithmetic order). We measure $p \in \{1,2,4,8,12,16\}$ on a
10-core/12-thread hybrid laptop CPU, study vectorisation at fixed $p$
(scalar vs.\ compiler default vs.\ explicit pragma), and repeat the run
confined to the four performance cores. Times are medians of five
repetitions; the sequential reference is measured around every thread sweep
to remove thermal drift. Parallelism pays off only from $n=200$ upward and
stops scaling around $p=8$--$12$: the best speedup is $2.59\times$ at
$n=2000$, and efficiency never exceeds $0.77$. With one thread the parallel
code is 26\,\% slower at $n=50$ (fork/join overhead). Running 16 threads on
12 execution contexts brings no gain and hurts small cases. Explicit SIMD is
worth 1.4--3.1$\times$ at fixed $p$, and the evidence shows GCC did not
vectorise the parallel loop by default. Confining the run to the performance
cores is 12--14\,\% faster at $n=2000$. All claims apply only to this
kernel, machine and protocol.
\end{abstract}

\section{Introduction and objective}

Assignments~1 and~2 produced a validated single-threaded baseline: a dense
$O(n^3)$ multiplication whose \texttt{ikj} loop order is the fastest local
variant on this machine~\cite{strang2016,cormen2022}. This assignment
studies how the same kernel behaves with several hardware threads, and how
much of that behaviour comes from threads and how much from SIMD
vectorisation.

\textbf{Research question.}
How does the thread count $p$ change the multiplication time $T_p(n)$? For
which sizes is parallel execution faster than the sequential baseline? And
what speed comes from vectorisation alone, with the thread count fixed?

\textbf{Hypotheses (stated before measurement).}
\begin{enumerate}
  \item[H1:] Parallel speedup grows with $n$ but stays far below $p$:
        fork/join costs dominate small multiplications, and at large $n$
        memory bandwidth and the mixed P/E cores limit scaling.
  \item[H2:] The parallel code with one thread shows the framework
        overhead: $T_p(1) \ge T_{seq}(n)$, with the largest gap at small
        $n$.
  \item[H3:] Running $p=16$ threads on 12 hardware contexts
        (oversubscription) brings no extra gain and is most costly for
        small multiplications.
  \item[H4:] At fixed $p$, the vectorised kernel is faster, with a smaller
        gain as $n$ grows and the multiplication becomes memory-bound; and
        compiler-default vectorisation of the parallel loop must not be
        assumed---it has to be checked per binary.
\end{enumerate}

\section{Background}

\textbf{Speedup and efficiency.}
With $T_{seq}(n)$ the sequential time and $T_p(n)$ the parallel time for
the same input, $S(p)=T_{seq}(n)/T_p(n)$ and $E(p)=S(p)/p \le 1$ for a
workload that does not change~\cite{fleming1986,mytkowicz2009}. A
superlinear value ($S(p)>p$) would signal a measurement or cache effect and
must be explained, not assumed~\cite{mytkowicz2009}.

\textbf{OpenMP.}
A \texttt{parallel for} loop forks $p$ threads, splits the outer index with
a static schedule, and joins at the end~\cite{openmp}. Each thread writes
disjoint rows of $C$, and the summation order over $k$ is unchanged, so
every $p$ gives bitwise-identical results. The inner loop over $j$ walks
contiguous memory, which suits vectorisation.

\textbf{Hybrid CPUs.}
The test laptop mixes performance cores (P-cores, two threads each) with
efficiency cores (E-cores, one thread each). Splitting rows evenly gives
every thread the same number of rows, but not the same cost: an E-core
takes longer per row than a P-core. This limits $E(p)$ and makes thread
placement part of the measurement~\cite{intelwapl}.

\textbf{SIMD.}
With \texttt{-march=native} the compiler targets AVX2 with FMA (32-byte
vectors, i.e.\ four doubles per vector; AVX-512 is disabled by the
toolchain). The \texttt{\#pragma omp simd} requests vectorisation
explicitly, and its effect must be measured at fixed $p$ so it is not mixed
with thread effects~\cite{intelig}.

\section{Methodology}

compiler flags. The sequential and parallel kernels do the same operations
in the same order (the parallel loop only distributes rows), so they are
equivalent; the documented differences are the OpenMP runtime and the SIMD

\subsection{Inputs}

Dense matrices for $n \in \{50,100,200,500,1000,2000\}$, generated as in
Assignments~1--2 (seed 42, uniform in $[-1,1]$, little-endian \texttt{<f8},
row-major) and reused byte for byte. A third buffer holds $C$, zeroed
inside the timed kernel.

\subsection{Correctness}

The self-test (run on all four binaries; 31 checks for \texttt{seq}, 76 for
the parallel builds; 0 failures) verifies known products, zero and identity
matrices, and random cases against a long-double reference
($\textit{rtol}=10^{-10}$, $\textit{atol}=10^{-12}$). For the parallel
builds it also checks \textbf{bitwise invariance} for $p \in
\{2,3,4,8,12\}$. During the campaign every measured batch emits a checksum
of $C$: among 222 configs and 1{,}110 measurements there is exactly one
distinct checksum per $n$, i.e.\ all variants, thread counts and affinities
produced identical matrices.

\subsection{Measurement protocol}

Each configuration (variant $\times$ $p$ $\times$ $n$ $\times$ affinity)
follows the protocol of Assignment~2:
\begin{enumerate}
  \item \textbf{Probe:} one unchecked warm-up plus two timed single
        multiplications; a config is skipped if a probe exceeds 60\,s.
        The bench budget is $\min(60\,\text{s}, 2\times
        \max(\text{probe, probe warm-up}))$; the warm-up term covers the
        cost of creating the thread team, which the bench process pays
        again.
  \item \textbf{Bench:} one warm-up, batch doubling until a batch lasts
        $\ge 0.2$\,s, then 5 measured repetitions of a full multiplication
        (kernel time only: loads and checksums are outside the timed
        region; \texttt{memset} of $C$ is inside, as part of a complete
        multiplication).
  \item \textbf{Summary statistic:} the \textbf{median} of the 5
        repetitions; variability is the coefficient of variation (CV).
        Memory is the peak resident set size of the process. Budgets: 60\,s
        and 4\,GiB per child; every run is stored as JSON lines in
        \texttt{data/results/raw\_detail/}.
\end{enumerate}

\textbf{Thermal drift control.}
A pilot campaign showed that results moved between sessions on this
laptop: the same binary and config measured $3.22$\,s and $4.35$\,s
($+35$\,\%) in two sessions, and $S(1)$ fell to 0.66--0.76. The reported
session therefore (1) warms up the machine for about 2.5\,min with
sustained 12-thread multiplications, and (2) \emph{brackets} every thread
sweep: for each $n$ the sequence is \texttt{seqpre} $\rightarrow$ $p \in
\{1,\dots,16\}$ $\rightarrow$ \texttt{seqpost}, and $T_{seq}(n)$ is the
median of the 10 bracketed sequential runs, measured seconds apart from
the sweep. The \texttt{simd2} and \texttt{pcore2} blocks run in the same
session, one after the other. All 96 stable-session configs and all 126
earlier configs finished with status \texttt{ok}; the earlier rows stay in
the CSVs for transparency, and the report quotes only the stable session.

\textbf{When does parallelism help?}
Only for $n \ge 200$. At $n=50$ every parallel run is slower than
sequential. At $n=100$ the parallel time stays flat at $\approx0.16$\,ms
for $p \le 8$: the fixed cost of the parallel region ($\sim$15--30\,$\mu$s
per multiplication at this size) dominates, and extra threads do not
shorten it. For $n \ge 200$ the time falls up to $p=8$ and then
saturates. The best speedups are $S(12)=2.56$ at $n=1000$ and $S(16)=2.59$
at $n=2000$; $E$ is at most $0.77$ everywhere (best at $p=2$ for $n \ge
200$). No configuration is superlinear. The single point above parity at
$p{=}1$, $S(1)=1.07$ at $n=200$, lies inside that config's 8.2\,\% CV and
is not claimed as a real gain.

Table~\ref{tab:simd} and Figure~\ref{fig:simd} quantify H4. The pragma is
worth 3.10$\times$ at $n=200$ but only 1.44$\times$ at $n=2000$ ($p=1$).
At $n=200$ the working set fits in cache, so the run is compute-bound and
close to the 4$\times$ width of 256-bit vectors over scalar code; at
$n=2000$ the three 32\,MB matrices are streamed from DRAM, and arithmetic
is no longer the bottleneck. The gain remains at high thread counts
(1.47--1.83$\times$ at $p=8$): vectorisation and threads compose. Their
effects stay separate by construction: every row of
Table~\ref{tab:scaling} uses the \texttt{simd} binary, while
Table~\ref{tab:simd} varies only the binary at fixed $p$.

\subsection{Oversubscription at $p=16$}

The hardware has 12 execution contexts, so $p=16$ is an oversubscribed
configuration (H3). At $n=2000$, $p=16$ is inside the variability of $p=12$
($S$: 2.59 vs.\ 2.57, i.e.\ $+0.8$\,\%, below the 3.7--3.9\,\% CV of both
configs): no gain, but no collapse either. At $n=1000$ it is 2\,\% slower;
at $n=100$, 10\,\% slower than $p=12$; at $n=50$, 28\,\% slower: sixteen
thread wake-ups and barrier crossings are paid for a kernel that is shorter
than the parallel region itself. Efficiency at $p=16$ never exceeds 0.16.
Oversubscription is therefore pointless: the extra threads only compete for
the same 12 contexts and add scheduling cost exactly where the useful work
is smallest.

\subsection{Memory}

Peak resident memory is 5.4, 6.2, 11.0, 28.2 and 96.8\,MB for $n=50, 200,
500, 1000, 2000$. At $n=2000$ this is essentially $3 \times 32$\,MB of
matrices plus process overhead, and it does not depend on $p$: static row
partitioning allocates no per-thread copies and creates no races
(consistent with the checksum invariance).

\section{Discussion}

\textbf{Answer to the research question.}
On this machine and kernel, parallel execution helps only from $n=200$
upward and only up to about $p=8$--$12$; the measured ceiling is
$S \approx 2.6$, far below $p=12$. Three effects add up: (1) fixed
parallel-region costs, which are 26\,\% of an $n=50$ multiplication and
explain the flat $n=100$ curve; (2) core heterogeneity: an equal row split
is not equal work on 2 P-cores + 8 E-cores, and the P-cores-only run beating
all-CPU scheduling by up to 14\,\% at $n=2000$ shows that placement matters
at large $n$; and (3) memory: at $n=2000$ the streaming of three 32\,MB
matrices limits useful parallelism and also caps the vectorisation gain at
1.44$\times$. H1--H4 are all supported, and H4's second part (default
vectorisation cannot be assumed) is demonstrated per binary.

\textbf{Methodological findings.}
Two instrument bugs were found and fixed before the reported session: a
gate that ignored the thread-team creation cost of the bench process (fixed
by including the probe warm-up in the gate), and cross-phase thermal drift
that depressed $S(1)$ to 0.66 (fixed by warm-up and sequential
bracketing). The pilot rows stay in the CSVs. The stability of the reported
session is visible as $S(1) \in [0.92, 1.07]$ for $n \ge 100$ and median CV
5.1\,\%.

\textbf{Limitations.}
\begin{itemize}
  \item One hybrid laptop, one kernel, one input distribution: results do
        not generalise to servers, other BLAS libraries or structured
        data.
  \item Windows places threads inside the affinity mask; P/E placement and
        boost states were not pinned per thread, so $\pm 5$--13\,\%
        run-to-run variability remains (median CV 5.1\,\%).
  \item At $p=1$ a residual $\pm 8$\,\% gap remains between baseline and
        parallel binary (drift, scheduling), so $S(1)$ is parity within
        noise, not an exact 1.00.
  \item No hardware performance counters were collected on Windows, so
        efficiency losses are not split into bandwidth and other terms.
  \item The missing vectorisation of the \texttt{auto} build is a GCC 16
        \texttt{-O2} cost-model decision; other compilers or \texttt{-O3}
        may differ.
\end{itemize}

As the assignment requests, the claims are limited to these
implementations, inputs and hardware~\cite{fleming1986,mytkowicz2009}.

\section{Conclusions}

Within the tested scope:
\begin{enumerate}
  \item The OpenMP row-parallel \texttt{ikj} kernel beats its sequential
        baseline only for $n \ge 200$, with a peak of $S(12)=2.56$
        ($n=1000$) and $S(16)=2.59$ ($n=2000$): threads buy at most about
        $2.6\times$ on 12 hardware contexts.
  \item Efficiency is the binding metric: $E(p) \le 0.77$ everywhere and
        $\le 0.21$ for $p \ge 12$, because of fixed parallel-region cost at
        small $n$ and of P/E asymmetry plus memory bandwidth at large $n$.
  \item The one-thread parallel overhead is 26\,\% at $n=50$ and within
        $\pm 8$\,\% of parity for $n \ge 200$.
  \item Oversubscription ($p=16$ on 12 contexts) gives no gain at large $n$
        and costs up to 28\,\% at $n=50$: it hurts exactly where the work
        per thread is smallest.
  \item Explicit \texttt{\#pragma omp simd} is worth 1.4--3.1$\times$ at
        fixed $p$, was necessary because GCC did not vectorise the parallel
        loop by default, and composes with threading.
  \item Confining the process to the four P-core threads is 12--14\,\%
        faster at $n=2000$.
\end{enumerate}

Open questions: whether a core-weighted row partition raises the scaling
ceiling, whether tiling relieves the bandwidth limit, and how these results
compare with a distributed implementation (Assignment~4).
